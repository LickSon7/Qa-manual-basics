Модуль 1 (Часть 1)

1. SDLC / STLC

SDLC — это процесс создания продукта от идеи до вывода его на рынок и иногда до закрытия проекта.

Основные этапы SDLC:

1. Сбор и анализ требований (что нужно сделать).
2. Дизайн и архитектура (как это будет выглядеть и устроено).
3. Разработка (кодинг) (написание самого кода).
4. Тестирование (проверка работоспособности).
5. Развертывание (deployment) — доставка и установка нового кода, конфигурации на серверы. (Релиз — выпуск продукта пользователям).
6. Поддержка (обновления, исправление ошибок в процессе работы).


STLC (Software Testing Life Cycle) — это последовательный процесс тестирования ПО для проверки его качества, идет параллельно с SDLC.

1. Сбор и анализ требований / Анализ требований
Маркер списка QA: Ищет логические ошибки и нестыковки в ТЗ до написания кода.
2. Проектирование и дизайн / Планирование тестирования
Маркер списка QA: Пишет Тест-план (сроки, инструменты, стратегия).
3. Разработка (Написание кода) / Разработка тест-кейсов
Маркер списка QA: Пишет пошаговые инструкции (тест-кейсы) для будущей проверки.
4. Тестирование / Выполнение тестов (Тестирование)
Маркер списка QA: Ищет баги, оформляет баг-репорты, перепроверяет исправления.
5. Развертывание (Деплой) / Smoke-тестирование (Проверка на бою)
Маркер списка QA: Быстро проверяет приложение на «живом» сервере сразу после запуска.
6. Поддержка и обслуживание / Регрессионное тестирование
Маркер списка QA: Проверяет, не сломали ли новые обновления старый рабочий код.



2. Виды тестирования

Маркер списка Валидные данные — правильно вводимые данные пользователя.
Маркер списка Невалидные — наоборот.

Позитивное и негативное тестирование
1. Позитивное — проверка того, правильно ли работает программа при вводе валидных данных.
2. Негативное — проверка на то, как программа реагирует на ввод невалидных данных.


⚠️ Важно: Если программа не прошла позитивные проверки, нет смысла начинать проверять негативные!


Функциональное тестирование — это широкий класс проверок, который отвечает на вопрос: «Делает ли программа то, что от неё задумывалось и прописано в требованиях?» Оно охватывает весь функционал приложения (как основные, так и второстепенные фичи), проверяет позитивные и негативные сценарии, граничные значения и детальную логику работы. Оно может занимать много времени.


Нефункциональное тестирование — это проверка того, как приложение работает. Сюда относятся удобство использования (usability), скорость и производительность, безопасность, надёжность, совместимость с разными устройствами и браузерами.


Дымковое тестирование (Smoke Testing) — это самая первая и поверхностная проверка самых главных, критически важных функций приложения (так называемых «путей счастья» или Happy Path), без которых программа вообще не имеет смысла.


Регрессионное тестирование — это проверка уже готовой программы после внесения обновлений.


3. Техники тест-дизайна / Граничные значения

«Техники тест-дизайна» — это фундаментальная база QA-инженера. Главная цель этих техник — сократить количество проверок, сохранив максимально высокое качество покрытия (протестировать всё ключевое и не писать 1000 одинаковых тестов).


Классы эквивалентности 

Классы бывают:
Валидные (позитивные): данные, которые программа должна принять.
Невалидные (негативные): данные, на которые программа должна выдать ошибку.

Анализ граничных значений - проверка значений на самых границах классов эквивалентности и рядом с ними.

Почему это важно?

Разработчики чаще всего ошибаются в условиях кода (> вместо >=, < <= и т.д.). Ошибки почти всегда «живут» на границах.

Формула проверок: {N - 1, N, N + 1}, где {N} — сама граница:
Маркер списка {N} — точка на границе.
Маркер списка {N - 1} — точка сразу слева / меньше границы.
Маркер списка {N + 1} — точка сразу справа / больше границы.

Пошаговая инструкция проведения проверки:

1. Изучить требования (ТЗ) — выяснить, какие значения разрешены, а какие запрещены (диапазоны, типы данных, ограничения).

2.Выделить классы эквивалентности — разбить все возможные варианты на группы: 1 валидную (где всё проходит) и несколько невалидных (где система должна выдать ошибку).

3. Выбрать представителей классов — взять по 1 значению из каждой группы для базовой проверки поведения системы.

4. Определить граничные значения — найти стыки между классами и составить проверки по формуле \bm{N-1, N, N+1} для каждой границы.

5. Выполнить проверки и зафиксировать результат — ввести подготовленные значения в поле и убедиться, что система реагирует строго по ТЗ.
